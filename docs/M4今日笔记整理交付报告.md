## 一、为什么做这件事

M3 让捕获变得无痛了，但留下一个断层：

```
读文章 → ⌥⌘E 静默攒进今日笔记 → ……然后呢？
```

今日笔记是个**只进不出的流水账**。攒到 20 条之后，你还是得自己想办法把它们分门别类搬走——而"手动复制粘贴到另一个文件"正是这个 App 本来要消灭的那种麻烦。

M4 补的就是这一段。

**能做的事：**

| 操作 | 说明 |
|---|---|
| 多选 | 勾选框，或直接点整行；有「全选 / 取消选择」 |
| 归档 | 移到已有主题笔记，**或现场新建一篇** |
| 删除 | 摘错了直接删掉 |
| 打开原文 | 每条右边的 ↗ 直接跳原文 |

**归档的语义是「移动」而不是「复制」**——今日笔记是收件箱，处理完就该清空。这样第二天打开，看到的就是干净的新一天。

**归档时标题会重写**，把日期补进去：

```markdown
# 今日笔记里                  →   # 主题笔记里
## 11:04 · 文章甲                  ## 2026-09-18 11:04 · 文章甲

> 第一条摘录内容                    > 第一条摘录内容

[原文链接](https://...)            [原文链接](https://...)
```

否则主题笔记里攒了几十条之后，全是 `## 11:04 · xxx`，根本分不清是哪天的。

## 三、实现上真正要小心的地方

### 编辑器内存 vs 磁盘文件的一致性

这是 M4 最容易出错的地方。归档要**改两个文件**（从今日笔记摘掉、往主题笔记追加），而这两个笔记**可能正开着窗口**。

如果此时编辑器内存里还有没落盘的输入，直接改文件会被编辑器的下一次自动保存覆盖回去，归档就白做了。

处理顺序：

```swift
NoteStore.shared.flush()          // 1. 先把编辑器里没落盘的输入写下去
...改今日笔记（原子写）...
...追加目标笔记（原子写）...
NoteWindowManager.reloadFromDisk([dailyID, target], force: true)   // 2. 强制让窗口重新读盘
```

`force: true` 是关键——正常情况下外部改动同步会**跳过有未保存输入的窗口**（M2 加的防覆盖保护），但归档是我们自己正式改写的文件，优先级高于内存状态，所以走强制路径。

### 原子写收口

顺手把 `NoteStore` 的写路径重构了：原来 `appendText` 自己复制了一份"临时文件 + replaceItemAt"的逻辑，现在统一收到唯一的 `writeNow` 里，`appendText` / `replaceAll` 都走它。少一处重复就少一处出错。

## 四、验证结果

```bash
"./dist/悬浮笔记.app/Contents/MacOS/FloatNotes" --selftest   # exit = 0
```

M4 阶段输出：

```
[selftest] 阶段14 · M4 今日笔记整理
[selftest] 解析出 3 条：
   · [11:04] 文章甲 | url=https://example.com/a | 第一条摘录内容
   · [11:04] 文章乙 | url=https://example.com/b | 第二条摘录内容
   · [11:04] 论文丙 | url=无 | 第三条摘录内容
[selftest] 归档 2 条 → 自检主题笔记；今日笔记剩 1 条，目标笔记收到 2 条
[selftest] 删除剩余条目后今日笔记剩 0 条
[selftest] PASS ✅
```

断言覆盖了：条目数、时间提取、URL 提取（含**无链接条目不该解析出 URL**）、预览生成、归档数量、今日笔记是否真的减少、目标笔记是否收到内容、**未勾选的条目有没有被误归档**、日期前缀是否补上、来源链接有没有丢、删除后是否清空。

窗口渲染冒烟（`--settings-smoke`）：

```
[smoke] 设置窗口 1 个 {{734, 131}, {480, 792}}
[smoke] 整理窗口 1 个 {{734, 311}, {640, 612}}
[smoke] 整理窗口解析到 1 条摘录
[smoke] PASS ✅
```

### 自检又抓到一个问题（这次是我的测试写错了）

第一次跑失败：

```
[selftest] 解析出 5 条          ← 期望 3 条
✗ 解析条目数不对（5，期望 3）
```

原因：**阶段13（M3 的今日笔记测试）在同一个文件里留了 2 条摘录**，阶段14 没清场就开工，于是把 5 条全解析了出来，连带"归档前两条"也挑错了对象。

这正是断言写得够细的好处——如果只检查"归档是否成功"，它会**假装通过**，但归档的是错的内容。修法是阶段14 开头先 `delete` 再 `ensureNote`，从干净状态开始。

自检结束时会把造的笔记、附件、字体/字号设置全部还原，零残留（已验证）。

## 五、当前完整工作流

```
① 读文章，选中一段 → ⌥⌘E
      底部弹胶囊「✓ 已存入今日笔记 · 第 3 条」，不打断

② 继续读，重复 ①

③ 读完 → ⌥⌘G 整理
      勾选 → 选目标主题笔记（或新建）→ 归档选中
      今日笔记清空，内容带着日期和来源进了主题笔记

④ 随时 ⌥⌘K 搜索、⌥⌘T 回到今日笔记
```

| 快捷键 | 功能 |
|---|---|
| `⌥⌘E` | 划词捕获（静默存入今日笔记） |
| `⌥⌘G` | **整理今日笔记** |
| `⌥⌘T` | 打开今日笔记 |
| `⌥⌘K` | 搜索笔记 |
| `⌥⌘N` | 新建空笔记 |
| `⌥⌘H` / `⌥⌘R` / `⌥⌘L` | 显隐全部 / 全部收起 / 覆盖菜单栏 |

## 八、已知限制

| # | 限制 | 说明 |
|---|---|---|
| L-1 | 归档目标只能是"已有笔记"或"新建" | 没有层级目录、没有标签、没有拖拽排序 |
| L-2 | 只能整条归档，不能拆分 | 一条摘录不能只把其中一句挑走 |
| L-3 | 归档不可撤销 | 归错了要手工从目标笔记搬回来 |
| L-4 | 没有批量选择"这一篇的所有摘录" | 只能全选或逐条勾。同一来源的多条没法一键挑出 |
| L-5 | 主题笔记没有自动推荐 | 不会根据内容建议归到哪一篇 |

## 九、M5 候选

按对闭环的价值排序：

1. **按来源分组 + 一键归档** —— 同一篇文章的摘录通常归到同一篇笔记。列表里按来源分组，一次勾一组，比逐条点快得多。
2. **撤销归档** —— 归错了能一键撤回（把条目从目标笔记搬回今日笔记）
3. **主题笔记推荐** —— 根据摘录内容里的关键词，建议几个候选目标
4. **摘录去重** —— 同一段选中两次会存两条
5. **AI 摘要** —— 读完一篇文章，把今日笔记里这篇的所有摘录合成一段总结
6. **图标设计 + iCloud / Git 同步**
