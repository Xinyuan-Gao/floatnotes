## 二、证据

### 证据 1 · 窗口层级表（系统 API 实测）

用 `CGWindowListCopyWindowInfo` 读取真实窗口层级。列表**从前到后**排列：

```
序  进程           层级   PID   窗口 / 位置
--------------------------------------------------------------
11  Window Server  24    168   Menubar (0,0 1470x33)
12  程序坞          20    1057  Dock (0,0 1470x956)
13  悬浮笔记         3    7663  欢迎        ★ (1026,57 420x340)   ← 笔记窗口
14  悬浮笔记         3    7663  (无标题)     ★ (1400,430 52x53)    ← 悬浮球
15  DSH Desktop     0    5205  (无标题)      (135,58 1304x792)
16  Warp            0    1184  ...           (135,57 1335x812)
```

**读出来的三件事：**

1. 笔记窗口与悬浮球都在 **层级 3**（`kCGFloatingWindowLevel`），普通应用窗口是 **层级 0** → 永远在上面。
2. 它们排在 `DSH Desktop`、`Warp` **之前** → 在窗口栈中确实位于这些应用之上。
3. **层级 3 < 程序坞 20 < 菜单栏 24/25**。这是重要发现：
   - 好处：不会遮住菜单栏和 Dock，符合直觉；
   - 代价：**盖不住菜单栏**。如果希望连菜单栏也盖住，需要把层级提到 `.statusBar`(25) 或更高——代码里已经预留了 ⌥⌘L 一键切换。

### 证据 2 · 跨全屏 Space 覆盖（决定性）

这是整个项目**风险最高**的一条。做法：另写一个测试 App，让它用系统原生方式进入全屏（绿色按钮那种，会新建一个 Space），然后在全屏状态下重新读取窗口层级表。

```
序  进程      层级  PID   窗口 / 位置
--------------------------------------------------------------
0   fstest    26   7742  (无标题) (0,0 1470x33)
1   DSH LAMP  25   5587  DSH LAMP (12,45 199x65)
2   Window Server 24 168 Menubar (0,0 1470x33)
3   悬浮笔记    3   7663  (无标题)  ★ (1400,430 52x53)        ← 悬浮球
4   悬浮笔记    3   7663  欢迎       ★ (1026,57 420x340)      ← 笔记窗口
5   fstest     0   7742  (无标题) (0,33 1470x32)
6   fstest     0   7742  FULLSCREEN-TEST-APP (0,33 1470x923)  ← 已全屏
```

`fstest` 的窗口已经是 `1470x923`（全屏），**而悬浮笔记的两个窗口依然出现在屏幕上、层级 3、并且排在全屏窗口之前**。

> **结论：切换 Space 进入全屏后，笔记窗口跟着过去了，并且浮在全屏 App 之上。核心需求成立。**

生效的三行配置：

```swift
panel.level = .floating
panel.collectionBehavior = [.canJoinAllSpaces,   // 所有桌面都出现
                            .fullScreenAuxiliary, // ★ 能浮在别的 App 全屏之上
                            .stationary]          // 切 Space 时不跟着滑动
panel.isFloatingPanel = true
panel.hidesOnDeactivate = false
```

## 三、关键技术发现（会影响后续设计）

### 发现 1 · Markdown 往返是「一次性有损、之后幂等」的 ⚠️ 重要

BlockNote 导出 Markdown 时会做规范化：

| 输入 | 导出 |
|---|---|
| `- 第一项` | `* 第一项` |
| 列表项之间无空行 | 每项之间插入空行 |

关键在于：**这个规范化只发生一次**。把规范化后的内容再喂回去，导出结果完全一致（实测两遍 124 字符完全相同）。

**这意味着「Markdown 作为唯一真源」是可行的**，不会出现每次保存都改文件、Git 永远有 diff 的问题。

**但需要接受的代价：** 用户用 Obsidian / VS Code 手写的 `-` 列表，第一次被本 App 打开保存后会被改成 `*`。如果这个不可接受，M1 需要改为「BlockNote JSON 为真源 + Markdown 作为导出/旁路」。

> **建议**：M1 先按 Markdown 真源做（可移植性优先），把 JSON sidecar 作为可选项后置。

### 发现 2 · `.floating`(3) 盖不住菜单栏

层级关系已实测：`普通窗口 0 < floating 3 < Dock 20 < 菜单栏 24/25`。

代码里已经内置了层级阶梯切换（⌥⌘L）：

```
.floating (3) → .statusBar (25) → .screenSaver (1000)
```

M1 建议做成设置项："是否允许盖住菜单栏 / Dock"。

### 发现 3 · 单文件 HTML 方案完全可行

用 `vite-plugin-singlefile` 把 React + BlockNote 全部内联进一个 2.6 MB 的 `index.html`，WKWebView 用 `loadFileURL` 直接加载，**绕开了 `file://` 下 ES module 和 CORS 的全部麻烦**。

不需要自定义 `WKURLSchemeHandler`，不需要跑本地 HTTP server。省掉一整块复杂度。

### 发现 4 · 冷启动与内存（待 M1 量化）

本次未测。M1 需要补测：单窗口内存占用、每增加一个窗口的增量、长时间挂机表现。

## 六、M1 建议调整（基于本次发现）

1. **存储**：先按 Markdown 真源做，接受一次规范化；把 JSON sidecar 列为 M2 可选项。
2. **层级**：把「是否盖住菜单栏 / Dock」做成设置项，而不是硬编码。
3. **补测**：内存占用、多窗口性能、中文输入法。
4. **补齐**：「全部收起」的默认行为（防窗口泛滥）、窗口位置记忆已实现但需打磨边缘吸附。
5. **可以砍掉的复杂度**：不需要 `WKURLSchemeHandler`，不需要本地 HTTP server，不需要 Xcode 工程文件。
