## 0. 一句话结论

**没有开箱即用的现成项目。** 但也不需要从零造——

- 「**永远置顶的悬浮窗口**」这件事，已经有至少 15 个开源项目做透了，方案高度收敛，可以直接抄架构；
- 「**富文本 / 块级编辑器**」这件事，开源生态极度成熟（TipTap / BlockNote / Lexical / NSTextView），可以直接抄轮子；
- **没人把这两件事按你要的方式拼在一起**：现有项目清一色是 Markdown 纯文本编辑器，不是 Word / 飞书那种富文本块编辑。

所以路线是：**站在 `chirami` 的架构肩膀上，换掉编辑器层**。工作量的大头不在"能不能置顶"，而在"编辑器体验"和"多窗口管理"。

另外有一个**必须先拍板的分叉**，见第 10 节：你要的是 **Word 式富文本**还是**飞书/Notion 式块编辑**——这两个是不同架构，选错了返工成本很高。

## 1. 需求拆解

把你的描述翻译成工程语言：

| # | 需求 | 工程含义 | 难度 |
|---|---|---|---|
| R1 | 屏幕上有一个按钮 | 常驻可见的启动器（悬浮球 / 菜单栏图标 / 全局热键） | ★ |
| R2 | 点击后出选项 | 一个轻量菜单：新建笔记 / 打开已有 / 最近笔记 | ★ |
| R3 | 点击新增笔记窗口 | 支持**多个**独立笔记窗口并存 | ★★ |
| R4 | 窗口凌驾于所有窗口之上 | `NSPanel` + 窗口层级 + 跨 Space + **全屏应用之上** | ★★★ |
| R5 | 富文本，像 Word / 飞书 | 块级编辑：标题、列表、待办、引用、代码块、表格、图片 | ★★★★★ |

**R4 和 R6 是这类 App 的真正技术门槛，R5 是工作量门槛。**

## 3. 先想清楚：你要的"富文本"是哪一种？

这是**最容易返工的地方**，两种"富文本"其实是两个产品：

| | **A. Word 式（连续文档流）** | **B. 飞书 / Notion 式（块编辑器）** |
|---|---|---|
| 心智模型 | 一篇文档，选中文字改格式 | 一叠积木，每块是一个语义单元 |
| 交互 | 加粗 / 斜体 / 字号 / 颜色 / 行距 | `/` 斜杠命令、块拖拽、块类型转换 |
| 典型结构 | 标题、段落、表格、图片 | 标题、待办、折叠块、引用、Callout、代码块、数据库 |
| 系统自带能力 | **NSTextView 天然支持** | ❌ 需要自己造 |
| Web 生态 | 一般 | **极度成熟（TipTap / BlockNote）** |
| 实现成本 | 低 | 中（用 BlockNote 则也低） |

> 你说的是"类似于 word 文档的那种或者说飞书的文档的写法"——这两个在你的语境里可能是一件事（"能加粗、有标题、有列表"），但工程上是两条路。**建议按第 10 节的问题确认。**

## 4. 技术选型

### 4.1 三个方案对比

| 维度 | **A. 纯原生**<br>Swift + AppKit + NSTextView | **B. 原生外壳 + Web 编辑器** ⭐推荐 | **C. 全 Web**<br>Tauri / Electron |
|---|---|---|---|
| 置顶 / 跨全屏能力 | 最强（原生 API 直控） | **同 A**（外壳还是原生） | 中（要穿一层抽象） |
| 不抢焦点 | 完全可控 | **同 A** | 较难 |
| 富文本开发成本 | 中（Word 式低，块式高） | **低**（TipTap/BlockNote 现成） | 低 |
| 内存占用 | ~50–80 MB | ~120–180 MB（多一个 WebView） | 300–500 MB |
| 冷启动 | < 0.5 s | ~1 s | 2–4 s |
| 手感 | 最原生 | 窗口原生，编辑区是 Web | 整体偏"网页" |
| 分发体积 | ~5 MB | ~15 MB | 60–150 MB |
| 参考实现 | Repotra、Stickies | **chirami**（Swift + CodeMirror 6） | Notiee、blink |

### 4.2 推荐：方案 B

**理由：**

1. **窗口行为交给原生**——置顶、跨 Space、不抢焦点、菜单栏、全局热键，这些是 AppKit 的强项，也是这个 App 的核心价值。
2. **编辑体验交给 Web**——你要的"飞书感"在 TipTap/BlockNote 生态里是现成的，原生要从零写块模型。
3. **有成功先例**——`chirami` 就是「Swift + NSPanel + WebView 编辑器」，已经验证这条路可行且体验好。
4. **编辑器可替换**——外壳和编辑器之间只走一层消息协议（`postMessage` / `WKScriptMessageHandler`），以后想换 Lexical 或换成原生 NSTextView，不动外壳。

> 如果 R5 最终确认是 **A（Word 式）**，那么推荐改为 **方案 A（纯原生 NSTextView）**：因为 Word 式富文本恰恰是 NSTextView 的主场，套 WebView 反而是多余的复杂度。

### 5.1 窗口与"永远置顶"（R4）

核心代码（**已在本机验证可编译通过**）：

```swift
final class NotePanel: NSPanel {
    override var canBecomeKey: Bool { true }    // 需要能打字
    override var canBecomeMain: Bool { true }
}

let panel = NotePanel(
    contentRect: NSRect(x: 100, y: 100, width: 420, height: 320),
    styleMask: [.nonactivatingPanel,   // ★ 点击不激活本 App
                .titled, .resizable, .fullSizeContentView],
    backing: .buffered, defer: false
)

panel.level = .floating                       // 常驻置顶
panel.collectionBehavior = [
    .canJoinAllSpaces,                        // 所有桌面都出现
    .fullScreenAuxiliary,                     // ★ 能浮在别的 App 全屏之上
    .stationary                               // 切 Space 不跟着滑动
]
panel.isFloatingPanel = true
panel.hidesOnDeactivate = false               // ★ 切走 App 不消失
panel.becomesKeyOnlyIfNeeded = true           // 只在需要时抢焦点
panel.isMovableByWindowBackground = true
```

配套：`Info.plist` 里 `LSUIElement = true`，让 App 不占 Dock、不抢主焦点。

**R6（不打断阅读）的关键**就是 `.nonactivatingPanel` + `becomesKeyOnlyIfNeeded`：点笔记窗口时，浏览器**仍然是前台 App**，但你可以直接在笔记里打字。这是系统级 Rich Text 便签都做不到的细节。

**层级升级阶梯**（如果 `.floating` 覆盖不了某些全屏场景，逐级往上试）：

```
.floating (3)  →  .statusBar (25)  →  .screenSaver (1000)  →  CGShieldingWindowLevel()
```

`chirami` 用 `.floating` 就宣称可用（对 tiling WM 友好），`obsidian_side_note` 宣称能盖住全屏应用。**这一条必须在 M0 阶段用真实场景实测**，见第 8 节风险 R-1。

| 形态 | 实现 | 优点 | 缺点 |
|---|---|---|---|
| **悬浮球** | 一个极小的置顶 `NSPanel`（~44×44），可拖到屏幕任意边缘，点击弹出菜单 | 最符合你说的"屏幕上有一个按钮" | 会一直占一点屏幕 |
| **菜单栏图标** | `NSStatusItem` / `MenuBarExtra` | 零打扰、永远可达 | 需要抬眼看菜单栏 |
| **全局热键** | `HotKey` / `KeyboardShortcuts`，如 `⌥⌘N` | 最快，手不离键盘 | 要记快捷键 |

菜单项设计：

```
＋ 新建笔记        ⌥⌘N
─────────────
📋 最近笔记
   · 2026-09-18 深度学习笔记
   · 未命名笔记 3
─────────────
📂 打开笔记库…
👁 显示/隐藏全部笔记   ⌥⌘H
🗂 全部收起
⚙️ 设置…
```

### 5.3 多窗口管理（R3）

```
NoteWindowManager
 ├─ [NoteID: NotePanel]            // 打开中的窗口
 ├─ open(noteID)                   // 已开则置前，未开则创建
 ├─ restoreFrames()                // 从 UserDefaults 恢复每个窗口的位置尺寸
 ├─ collapseAll()                  // 全部折叠成细条（像 Stickies 那样）
 └─ persistOnMove/Resize()         // 拖动结束即存位置
```

细节体验：
- **窗口位置记忆**——每个笔记记住自己的 frame，重启后原位恢复。
- **全部收起**——一键把所有笔记压成一条细栏，只在需要时展开（解决"窗口太多反而更乱"）。
- **边缘吸附**——拖到屏幕边缘自动贴边 + 可以只露出一条边。
- **每窗口独立透明度**——抄 chirami 的 per-note 透明度/主题。

### 5.4 编辑器层（R5）

- **若选 B（飞书式）**：`WKWebView` 加载本地打包的 BlockNote/TipTap 页面，Bridge 协议极简：
  ```
  Swift → JS : { type: "load", doc } | { type: "setTheme", value }
  JS → Swift : { type: "change", doc } | { type: "ready" } | { type: "export", format }
  ```
  用 `WKWebViewConfiguration` + `WKScriptMessageHandler` 实现，注意注入 `WKUserScript` 的时序。
- **若选 A（Word 式）**：直接用 `NSTextView`，配置 `isRichText = true`、`allowsUndo = true`、`usesFontPanel`、`isAutomaticQuoteSubstitutionEnabled` 等；表格用 `NSTextTable`，图片用 `NSTextAttachment`。**不引入 WebView，整个 App 可以做到 5 MB。**

### 5.5 数据与存储（R7）

| 方案 | 格式 | 优点 | 缺点 |
|---|---|---|---|
| **Markdown 单一真源** ⭐ | `.md` | 可移植、可用 Obsidian/VS Code 打开、Git 友好 | 表达不了折叠块/分栏等块特性 |
| Markdown + JSON sidecar | `.md` + `.json` | 内容可读 + 布局完整 | 两份数据要同步 |
| 纯 JSON（TipTap doc） | `.json` | 无损 | 不可读、锁定生态 |
| RTFD | `.rtfd` | 原生富文本 + 图片 | 生态孤岛 |

**建议**：`~/Documents/悬浮笔记/` 下以 **`.md` 为真源**，块级布局等 Markdown 表达不了的信息放同名 `.json` sidecar。理由：你是"读文章记笔记"，产出未来大概率要喂给别的工具，可移植性 > 保真度。

> **M0 修正（已实测）**：BlockNote 导出 Markdown 时会做一次性规范化——`- 列表` 变 `* 列表`，列表项之间补空行。
> 关键是好消息：**规范化只发生一次，之后完全幂等**（实测两遍落盘 124 字符完全一致），不会出现每次保存都改文件的问题。
> 所以 **Markdown 作真源可行**，代价是用户手写的 `-` 会被改成 `*`。若这一点不可接受，M1 改用「JSON 真源 + Markdown 导出」。
> 附带好消息：Markdown 里表达不了的块级特性暂时没遇到——标题、加粗、行内代码、列表、待办、引用、代码块全部无损往返。

配套：
- 编辑防抖 500 ms 落盘 + 原子写（写临时文件再 `rename`），避免崩溃丢数据。✅ 已在 M0 实现
- 用 `FSEvents` / `DispatchSource` 监听文件变化，实现"外部改了自动同步"（chirami 有这个特性）。⬜ M2

## 8. 风险与坑

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| **R-1** | ~~"盖住全屏应用"未必成立~~ | ✅ **已解除** | M0 已用真实全屏 App 实测：笔记窗口跟着进入全屏 Space 并浮在其上。`level=.floating` + `[.canJoinAllSpaces, .fullScreenAuxiliary, .stationary]` 即可 |

| **R-4** | WKWebView 内存占用随窗口数线性增长 | 🟡 中 | 限制同时打开的窗口数；长时间不用的窗口卸载 WebView 只留文本快照 |
| **R-5** | 无 Xcode，调试体验差（没有断点调试 UI） | 🟡 中 | 用 `os_log` + LLDB 命令行；`swift build` 快速迭代。撑不住再装 Xcode |
| **R-6** | App 未签名/未公证，Gatekeeper 拦截 | 🟢 低（自用） | 自用 `codesign -s -` 即可；要分发才需开发者账号（$99/年）+ 公证 |
| **R-7** | Markdown 表达不了块级特性（折叠、分栏、Callout） | 🟢 低 | sidecar JSON 兜底；M1 先只支持 Markdown 能表达的子集 |
